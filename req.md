<h1>[ДРАФТ] Требования ИБ к подсистеме контейнерной оркестрации</h1>

Здесь прорабатываются требования со стороны архитектуры ИБ для использования контейнерного оркестратора в рамках подсистемы ИС.
Здесь **не прорабатываются** требования для использования контейнерного оркестратора в рамках подсистемы ИС ТП или ИС ТП.

ДЭСЗИ - Департамент экспертизы и сервисов защиты информации

ПКО - Подсистема контейнерной оркестрации

ТУЗ - Техническая учетная запись

<h2>Архитектура подсистемы контейнерной оркестрации</h2>

1.* - требования к доставке и развертыванию ПО

| №| Требование| Комментарий|
| ---  | --- | --- |
|1.1   | Для хранения и доставки образов в ПКО должен использоваться развернутый в контуре ИС репозиторий AHRepo. В репозитории должны храниться только образы прошедшие процедуру проверки и согласования ДЭСЗИ БИБ. В репозитории должен быть реализован повторный аудит образов на соответствие требованиям ИБ| Необходимо утвердить единый подход для доступа к ИС AHRepo для таких систем. Проблематика - необходим прямой доступ от всех нод кластера к репозиторию AHRepo. |
|1.2   | Для процессов развертывания/обновления ПО запущенного на основе ПКО (как системного, так и прикладного) должен использоваться AhCode CD runner    |     |
|1.3   | Развертывание компонентов (прикладного и инфраструктурного ПО) должно осуществляться только через CI/CD систему (AhCode) с использованием менеджера пакетов helm, при этом необходимые секреты для развертывания должны храниться в отдельном контуре с ограниченным доступом    | Решение на базе Hashicorp Vault или аналогичное   |
|1.4   | Все метаданные для развертывания (кроме секретов) и настройки как ПКО так и сервисов запущенных на основе ПКО (Манифесты, конфигурации, helm чарты) должны храниться в выделенном проектном пространстве AhCode.    |     |
|1.5   | Все настройки и/или изменения  конфигурации ПКО так и сервисов запущенных на основе ПКО должны производиться через CI/CD с использованием системы версионирования кода |  |     
|1.6   | Должна быть спроектирована и проработана подсистема хранения и доставки секретов. В рамках ИС должен быть выстроен процесс управления секретами    | Не прорабатывалось для k8s. Не определен целевой способ доступа к секретам со стороны приложения запущенного в подсистеме оркестрации. Не внедрено ИЗ решение по хранению секретов |


2.* - требования по сегментации

| №| Требование| Комментарий|
| ---  | --- | --- |
|2.1   | Для каждого из контуров ИС использующей ПКО должны быть разработаны и  развернуты независимые инсталляции kubernetes |  |
|2.2   | Не допускается объединение нескольких ИС в одном кластере kubernetes |  |
|2.3   | Каждая инсталляция Kubernetes должна находиться в отдельном VLAN, изолированном от остальных компонентов ИС |  |
|2.4   | ПКО должна быть спроектирована с разделением на узлы-мастера, рабочие узлы и пограничные шлюзы (ingress nodes)  |  |
|2.5   | Внешние соединения к сервисам запущенным на основе ПКО должны осуществляться только через выделенные хосты (пограничные шлюзы/ingress). Все правила доступа с детализацией до конкретного сервиса должны документироваться и согласовываться на сетевой схеме. |  |
|2.6   | Исходящие соединения от сервисов запущенных в кластере должны осуществляться только через выделенные хосты (пограничные шлюзы/egress). Все правила доступа с детализацией до конкретного сервиса должны документироваться и согласовываться на сетевой схеме. |  |
|2.7   | Компоненты Ingress-Controller должны быть запущены только на выделенных хостах (пограничные шлюзы)|  |
|2.8   | Для всех внешних соединений (соединений с другими сегментами) должны использоваться только безопасные протоколы сетевого взаимодействия |  |
|2.9   | Для всех внутренних соединений (соединений между сервисами запущенными на основе ПКО) должны использоваться только безопасные протоколы сетевого взаимодействия |  |
|2.10   | Сетевые доступы в/из ПКО должны документироваться таким образом, чтобы они явно отражали интеграционное взаимодействие с детализацией до конкретного сервиса/микросервиса   |  |
|2.11  | Управляющие компоненты кластера (kube-api, kube-dashboard, deckhouse dashboard) не должны публиковаться и быть доступны вне контура ИС. Доступ к управляющим интерфейсам должен предоставляться через решение контроля привилегированных пользователей (СКДПУ) по аналогии с административным доступом по ssh. | Не проработано. Доступ к данным интерфейсам должен быть ограничен на сетевом уровне и предоставляться только сотрудникам ответственным за сопровождение ПКО согласно ролевой модели и матрице RACI ДСИТ. |

3.* - требования к интеграции с СЗИ, аудиту и доступу

| №| Требование| Комментарий|
| ---  | --- | --- |
|3.1   | ПКО должна быть интегрирована со службой каталогов Microsoft Active Directory для аутентификации пользователей и администраторов в управляющем интерфейсе платформы |  |
|3.2   | ПКО должна быть интегрирована со службой каталогов Microsoft Active Directory для аутентификации пользователей и администраторов в веб интерфейсах платформы |  |
|3.3   | ПКО должна содержать средства сбора логов и удаленной отправки в подсистему хранения. Подсистема хранения логов должна находиться вне кластера Kubernetes |  |
|3.4   | ПКО должна содержать средства генерации и сбора событий аудита и удаленной отправки в подсистему хранения аудита, а так же в SIEM-систему. Подсистема хранения аудита должна находиться вне кластера Kubernetes. События аудита регистрируемые средствами ПКО должны соответствовать требованиям документа "Регламент обеспечения информационной безопаности на стадиях жизненного цикла автоматизированных банковских систем ПАО Промсвязьбанк" |  |
|3.5   | ПКО должна быть интегрирована с СЗИ для Kubernetes - Luntry. Лицензии Luntry должны быть заложены при расчете сайзинга ИС для окружений содержащих защищаемую информацию  |  |

<h2>Аутентификация и авторизация</h2>

| №| Требование| Комментарий|
| ---  | --- | --- |
|1      | Аутентификация администраторов в API Kubernetes и других управляющих интерфейсах платформы должна происходить на основе групп AD. Для подключения kubernetes к AD допускается использование IdP.   
|2      | Администраторам кластера не допускается использовать токены service account или другие локальные ТУЗ для аутентификации в API Kubernetes и других управляющих интерфейсах платформы|    |
|3      | Названия ТУЗ должны отражать назначение УЗ и используемые права доступа    |     |
|4      | Для каждого кластера Kubernetes должна быть разработана и согласована ролевая модель    |    |
|5      | Для каждого кластера Kubernetes должны быть настроена авторизация на основе ролей Role-Based Access Control (RBAC). Права должны назначаться в пределах пространства имен по принципу наименьших привилегий и разделения полномочий   |     |
|6      | Каждый сервис, которому требуется взаимодействие с kubernetes api должен обладать уникальным Service Account (SA) с настроенными правами RBAC. Сервис аккаунты должны использоваться только в тех подах (pod), которым они требуются для работы. По-умолчанию использование SA должно быть запрещено с указанием опции “automountServiceAccountToken: false”. Создание SA должно быть согласовано с БИБ | Service Account Kubernetes - это ТУЗ. Его создание и права должны быть согласованы с БИБ  |
|7      | Запрещено использовать средства user impersonation (возможность выполнять действия под другой УЗ)   |     |
|8      | Запрещено использовать анонимную аутентификацию. Анонимная аутентификация должна быть отключена    |     |
|9      | Администраторы кластера и функциональное сопровождение должны взаимодействовать с API кластера и инфраструктурными сервисами через решение контроля привилегированных пользователей (СКДПУ)|     |
|11      | Компоненты информационной системы должны выноситься в отдельное пространство имен (namespaces) изолированно от системных компонентов ПКО    |     |
|12      | Использование роли cluster-admin допустимо только при первичной настройке кластера (bootstrap) Для администраторов кластера должна быть сформирована и описана и согласована отдельная роль на основе ролевой модели доступа |     |
|13      | Внесение изменений должно происходить на основании описаний (манифестов), при помощи AHCode CD раннера, запрещена интерактивная работа в консоли Kubernetes за исключением задач сопровождения платформы ответственным эксплуатационным подразделением.|     |

|6      | Должны фиксироваться все действия, связанные с развертыванием приложений и изменением их конфигурации   |     |
|7      | Должны фиксироваться все случаи изменения параметров, системных настроек или конфигурации всего кластера. В том числе средствами на уровне ОС   |     |
|8      | Должны фиксироваться все действия администраторов сопровождения и администраторов кластера, связанных с созданием и монтированием томов    |     |
|9      |  Должны фиксироваться все запросы от пользователя anonymous   |     |
|10      |  Должны фиксироваться все неудачные запросы к kube-api серверу   |     |
|11      |  Должны фиксироваться все действия администраторов сопровождения и администраторов кластера, связанные с изменением параметров контроллера доступа   |     |
|12      |  На всех нодах должно быть запущено решение для реализации мониторинга безопасности - Luntry   |     |
|13      | Подсистема хранения аудита должна быть расположена вне кластера Kubernetes   |     |

|15      | Должна обеспечиваться выгрузка выше перечисленных данных в формате syslog в SIEM.  Все компоненты системы должны экспортировать логи в режиме INFO (максимально информативный режим в зависимости от свойств источника, но не debug) на ptsiem. | Необходимо определить и утвердить тип протокола и формат сообщений для передачи данных в SIEM.    |


<h2>Сетевая конфигурация</h2>

| №| Требование| Комментарий|
| ---  | --- | --- |
|1      | Должен использоваться CNI с поддержкой механизма NetworkPolicy |  |
|2      | Все пространства имен должны обладать сетевыми политиками. Взаимодействия между пространствами имен должны быть ограничены NetworkPolicy по принципам наименьших привилегий. Политика должна ограничивать все взаимодействия между пространствами имён (namespaces) kubernetes , кроме тех взаимодействий, которые явно согласованы со стороны БИБ. Политики должны быть применены по умолчанию на уровне ingress и egress взаимодействий | Политика по умолчанию |
|3      | Ко всем рабочим нагрузкам (POD) должны быть применены сетевые политики по принципу deny-all. Разрешение трафика должно быть явным и минимально необходимым для работы системы  | Политика разрабатывается по отношению к каждому прикладному сервису/микросервису |
|4      | При организации микросервисного сетевого взаимодействия, необходимо, чтобы каждый сервис проходил аутентификацию и авторизацию и обеспечивал шифрование (mTLS)    |     |
|5      | Хранилища данных должны быть расположены в отдельном VLAN на изолированных нодах не относящихся к ПКО   | Должна быть создана и проработана отдельная подсистема хранения данных для интеграции оркестратора  |
|6      | Внешний интернет-трафик, проходящий внутрь кластера, должен инспектироваться с помощью WAF    |     |
|7      | Сетевой доступ к компоненту etcd должен иметь только компонент kube-api. Для остальных компонентов ПКО и сервисов запущенных на ее основе сетевой доступ должен быть ограничен    |     |
|9   | Публикация приложений из кластера должна происходить только с использованием механизма Ingress через выделенные шлюзы (ingress nodes) Запрещено использование публикации через HostPort или NodePort. |  |
|10   | Должны блокироваться все нешифрованные внутренние (внутри ПКО) взаимодействия |  |
|11   | Должны блокироваться все нешифрованные внешние (входящие/исходящие из ПКО) взаимодействия |  |
